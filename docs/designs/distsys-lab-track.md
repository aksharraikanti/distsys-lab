## Problem Statement
Learn distributed systems from zero prior background, one small daily task at a time: research a concept, implement it, commit it. The track is a 10-stage integrated build — Raft consensus → fault-tolerant KV store → connection pooling → caching → sharding → hot-shard splitting → distributed transactions → scale-to-zero orchestration → CDN edge layer → eventual consistency — culminating in a capstone deployed on real AWS infrastructure.

## What Makes This Cool
Most self-study distributed-systems material treats each concept as an isolated toy exercise (a Raft implementation here, a cache-aside demo there). This track is deliberately integrated: Stage 4's cache sits in front of Stage 2's KV store, Stage 6's hot-shard splitter operates on Stage 5's sharded version of that same store, and the capstone deploys the whole compounded system to AWS. By the time you reach hot-shard splitting, you're not following a tutorial — you're debugging load imbalance in a system you built the consensus layer for yourself.

## Constraints
- Solo project, paced at roughly one small task per day, alongside learning the underlying concept.
- Go, single monorepo (`distsys-lab`) — later stages import earlier stages as local packages, matching how the curriculum is designed to build on itself. Directory names carry the numeric prefix (`01-raft/`), but each directory's Go package name is the plain word (`package raft`) since Go identifiers can't start with a digit.
- No AWS setup until the capstone — Stages 1-9 run entirely local/simulated (in-process or localhost RPC).
- Zero prior distributed-systems background — daily tasks must be small enough (30-90 min) to sustain a daily cadence without stalling.
- Public GitHub repo — this doubles as a portfolio piece.

## Premises
1. Building Raft, the KV store, the pooling/caching layers, sharding, and transactions from scratch (never importing an existing consensus/raft library) is correct here — the goal is understanding internals, not efficiency. Production systems would never hand-roll this.
2. One small, single-concept task per day is the right granularity given zero prior background — bigger daily chunks risk stalling momentum on a solo, unsupervised track.
3. No AWS wiring happens before the capstone — earlier stages simulate everything locally, keeping cost and infra complexity at zero until the concepts are proven.
4. This is a learning/portfolio repo, not a shipped product — no packaging or distribution channel is needed beyond the public GitHub repo itself and its commit history.

## Approaches Considered
### Approach A: Structured stage scaffold (chosen)
Each stage gets its own directory (`01-raft/`, `02-kv-store/`, ...) with a `README.md` (concept notes filled in as learned, plus reference links), a `TASKS.md` (day-by-day checklist, 30-90 min chunks), a `tests/` directory, and a root `PROGRESS.md` tracking which day/stage is active across the whole track. GitHub Actions runs `go test ./...` on every push for a daily green/red signal.

### Approach B: Minimal flat checklist (rejected)
A single root `TASKS.md` listing every day across all 10 stages as checkboxes, code living directly in stage folders with no per-stage README or CI. Fastest to start, but loses the concept-notes trail and gives no automated signal when something breaks — mistakes surface later than they should on a track this long.

## Recommended Approach
Approach A. The per-stage README doubles as a running concept journal (valuable both for retention and as portfolio evidence of understanding, not just code), and CI gives a same-day correctness signal, which matters most on a 10-stage, multi-month solo track where later stages depend on earlier ones actually being correct.

## Open Questions
- Whether daily commits should be squashed per-stage before merging to main, or kept as-is for a granular history (default: kept as-is, matching the prior harness-project pattern of one commit per working day).
- Exact pacing for stages beyond Stage 1 — will be scoped stage-by-stage as each is reached, rather than front-loading a day-by-day breakdown for all 10 stages now.

## Success Criteria
- A public GitHub repo with roughly one commit per working day, each a small, reviewable, working increment.
- `PROGRESS.md` accurately reflects current stage/day at all times.
- Each stage's tests pass in CI before the next stage begins depending on it.
- By the end of Stage 4, a working connection-pooled, cached, Raft-backed KV store exists — a standalone, demoable, resume-worthy milestone per the original curriculum notes.
- Capstone: the compounded system (replicated, sharded, transactional, cached, autoscaling, edge-fronted) deployed on EC2/ECS + ElastiCache + S3/CloudFront.

## Distribution Plan
Public GitHub repo is the only distribution channel needed through Stage 9 — no packaging, no releases. The capstone's CI/CD (deploy to AWS) is scoped when that stage is reached, not now.

Get 3 in-process mock nodes talking over it.
   - Day 2: Server states — implement the Follower/Candidate/Leader state machine and state transitions (no elections triggered yet, just the state enum and transition rules).
   - Day 3: Election timeouts — randomized election timeout, trigger a Candidate transition when no heartbeat is received in time.
   - Day 4: Leader election — implement `RequestVote` handling and vote counting; get a single leader elected among 3 nodes with no network faults.
   - Day 5: Heartbeats — leader sends periodic empty `AppendEntries` as heartbeats; followers reset their election timer on receipt.
   - Day 6: Election edge cases — split votes, term numbers, stale-leader rejection; test with simulated node restarts.
   - Day 7: Log entries — extend `AppendEntries` to carry real log entries; leader appends to its own log on a client request.
   - Day 8: Log replication — leader replicates entries to followers, tracks `matchIndex`/`nextIndex`, retries on failure.
   - Day 9: Commit rule — leader advances `commitIndex` once a majority has replicated an entry; followers apply committed entries to a state machine.
   - Day 10: Log consistency check — implement the `AppendEntries` consistency check (prevLogIndex/prevLogTerm) so followers reject/truncate divergent logs.
   - Day 11: Persistence — persist term, vote, and log to disk so a crashed node recovers correctly on restart.
   - Day 12: Fault injection tests — using the fake transport from Day 1, simulate leader crashes, network partitions, and follower restarts; verify the cluster always converges to a single consistent log. This day is likely to spill into a Day 13 — partition testing is the hardest part of Stage 1, budget for it.
